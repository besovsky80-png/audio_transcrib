## Компоненты системы

### 1. Ingestion API (`ingest-api`)

**Назначение:** Приём аудио от источников

**Технологии:** FastAPI, WebSockets

**Эндпоинты:**
- `POST /calls` - создание сессии
- `WS /ws/audio` - потоковый приём аудио
- `WS /ws/transcripts/{session_id}` - подписка на транскрипт

**Входные данные:**
```json
{
  "event": "start_call",
  "source_type": "test_client",
  "sample_rate": 16000,
  "channels": 1,
  "consent_given": true
}
```

**Выходные данные:**
```json
{
  "type": "audio_accepted",
  "session_id": "uuid",
  "chunk_id": "uuid"
}
```

### 2. Audio Normalizer

**Назначение:** Приведение аудио к стандартному формату

**Функции:**
- Проверка формата (PCM 16-bit, 16kHz, mono)
- Конвертация из других форматов
- Нарезка на чанки по 250 мс
- Расчёт timestamp_ms для каждого чанка
- Отбраковка битых/коротких чанков

### 3. Voice Activity Detection (VAD)

**Назначение:** Определение наличия речи в аудио

**Технологии:** silero-vad или webrtcvad

**События:**
- `speech_start` - начало речевого сегмента
- `speech_end` - конец речевого сегмента
- `speech_detected: bool` - флаг наличия речи

**Параметры:**
- `VAD_THRESHOLD` - порог чувствительности (по умолчанию 0.5)

### 4. Message Broker

**Назначение:** Асинхронная коммуникация между компонентами

**Технологии:** Redis Streams

**Потоки:**
- `audio.raw` - сырые аудио-чанки
- `audio.speech` - чанки с речью (после VAD)
- `asr.partial` - частичные транскрипты
- `asr.final` - финальные транскрипты
- `diarization.results` - результаты диаризации
- `call.events` - события звонка (start, end, error)

### 5. ASR Worker

**Назначение:** Распознавание речи в текст

**Технологии:** faster-whisper

**Модели:**
- `tiny` - быстрая, для CPU
- `base` - баланс скорости и качества
- `small` - лучшее качество

**Процесс:**
1. Чтение из `audio.speech`
2. Транскрибация чанка
3. Публикация в `asr.partial` (промежуточный результат)
4. Публикация в `asr.final` (финальный результат)
5. Сохранение в БД

### 6. Diarization Worker

**Назначение:** Разделение речи по спикерам

**Варианты реализации:**

**A. Полноценная (pyannote.audio):**
- Загрузка модели
- Анализ аудио
- Определение спикеров

**B. Упрощённая (fallback):**
- Разделение по каналам (если стерео)
- Энергетические пороги
- Маркировка: speaker_0, speaker_1

**Результат:**
```json
{
  "segments": [
    {"start_ms": 0, "end_ms": 3000, "speaker": "speaker_0"},
    {"start_ms": 3000, "end_ms": 5000, "speaker": "speaker_1"}
  ]
}
```

### 7. Postprocessing

**Назначение:** Финальная сборка и обработка результатов

**Функции:**
- Объединение ASR-сегментов
- Привязка спикеров к сегментам
- Сортировка по времени
- Удаление дубликатов
- Маскирование PII (телефоны, email, карты)
- Формирование итогового объекта

**Результат:**
```json
{
  "session_id": "uuid",
  "duration_ms": 62000,
  "segments": [
    {
      "start_ms": 0,
      "end_ms": 3000,
      "speaker": "speaker_0",
      "text": "Здравствуйте"
    }
  ],
  "full_text": "Здравствуйте ...",
  "language": "ru",
  "status": "completed"
}
```

### 8. Database

**Назначение:** Хранение метаданных и результатов

**Технологии:** PostgreSQL 16, SQLAlchemy, Alembic

**Таблицы:**
- `call_sessions` - сессии звонков
- `audio_segments` - аудио-сегменты
- `transcript_segments` - сегменты транскрипта
- `speaker_segments` - сегменты спикеров
- `job_status` - статусы обработки
- `consent_records` - записи о согласии

### 9. Storage

**Назначение:** Хранение аудиофайлов

**Технологии:** MinIO (S3-compatible) или локальная папка

**Структура:**
```
calls/
  {session_id}.wav
  {session_id}.json
```

**В БД:** ссылка `audio_url`

### 10. API / UI

**Назначение:** Предоставление доступа к результатам

**REST API:**
- `GET /health` - проверка здоровья
- `GET /metrics` - метрики
- `POST /calls` - создание звонка
- `GET /calls` - список звонков
- `GET /calls/{session_id}` - детали звонка
- `GET /calls/{session_id}/transcript` - транскрипт
- `GET /calls/{session_id}/audio` - аудиофайл
- `DELETE /calls/{session_id}` - удаление

**Веб-интерфейс:**
- `/` - главная страница
- `/calls` - список звонков
- `/calls/{session_id}` - детали звонка с транскриптом

## События и топики

### События звонка

| Событие | Описание | Топик |
|---------|----------|-------|
| call.started | Звонок начат | call.events |
| call.audio_received | Аудио получено | call.events |
| call.speech_detected | Речь обнаружена | call.events |
| call.transcript_partial | Частичный транскрипт | asr.partial |
| call.transcript_final | Финальный транскрипт | asr.final |
| call.completed | Звонок завершён | call.events |
| call.failed | Ошибка обработки | call.events |

### Формат событий

```json
{
  "event_type": "call.started",
  "session_id": "uuid",
  "timestamp": "2024-01-01T00:00:00Z",
  "data": {...}
}
```

## Последовательность обработки

1. Клиент подключается к `WS /ws/audio`
2. Отправляет метаданные звонка
3. Сервер создаёт сессию, возвращает `session_id`
4. Клиент отправляет аудио-чанки
5. Сервер нормализует аудио, нарезает на чанки
6. VAD определяет речь
7. Речевые чанки публикуются в `audio.speech`
8. ASR Worker читает чанки, распознаёт текст
9. Частичные результаты публикуются в `asr.partial`
10. Финальные результаты публикуются в `asr.final`
11. Diarization Worker разделяет спикеров
12. Postprocessing собирает итоговый транскрипт
13. Результаты сохраняются в БД и хранилище
14. Клиент может получить результаты через API

## Масштабирование

### Горизонтальное масштабирование workers

```
┌─────────────┐
│ Redis       │
│ Streams     │
└──────┬──────┘
       │
       ├──► ASR Worker #1
       ├──► ASR Worker #2
       └──► ASR Worker #N
```

### Ресурсные требования

**Минимальные (локально):**
- CPU: 2 cores
- RAM: 4 GB
- Disk: 10 GB

**Рекомендуемые (production):**
- CPU: 4+ cores
- RAM: 8+ GB
- GPU: опционально для ASR
- Disk: 100+ GB

## Безопасность

### Аутентификация
- API ключи (`X-API-Key`)
- JWT токены (опционально)

### Шифрование
- HTTPS/TLS в production
- Шифрование данных в покое (S3)

### Логирование
- Structured logs с session_id
- Audit log операций удаления
- Мониторинг попыток доступа без ключа
